# Задание 2. Выбор и настройка мониторинга в системе

## 1. Мотивация

Текущие проблемы:
- Яндекс Метрика не показывает B2B-трафик через API
- Проблемы обнаруживаются через жалобы клиентов
- Нет данных о производительности системы
- Нет алертов при сбоях

Что даст бизнесу:
- Снижение потери заказов - сохранение B2B контрактов
- Быстрое обнаружение проблем - время простоя с часов до минут
- SLA для клиентов - гарантия доступности 99.9%
- Оптимизация ресурсов - понимание где масштабировать

Целевые показатели:
- MTTD (время обнаружения): с часов до 5 минут
- MTTR (время восстановления): с часов до 15 минут
- Проактивное обнаружение: 90% проблем до жалоб клиентов

## 2. Выбор подхода к мониторингу

Для API-сервисов (Shop, CRM, MES): RED метод
- Rate - запросы в секунду
- Errors - процент ошибок
- Duration - время выполнения

Для ресурсов (PostgreSQL, RabbitMQ, EC2): USE метод
- Utilization - процент использования
- Saturation - очередь ожидания
- Errors - ошибки ресурса

Для бизнес-метрик: кастомные метрики
- Заказы по статусам
- Время расчёта стоимости
- Потерянные сообщения

## 3. Метрики для мониторинга

### 3.1 API-сервисы

**http_requests_total (counter)**
Зачем: отслеживать нагрузку, видеть аномалии
Ярлыки: service, method, endpoint, status_code

**http_request_duration_seconds (histogram)**
Зачем: SLA для клиентов, обнаружение деградации
Ярлыки: service, endpoint
Перцентили: p50, p95, p99

**http_requests_errors_total (counter)**
Зачем: быстро видеть проблемы (5xx = проблема на сервере)
Ярлыки: service, status_code, endpoint

### 3.2 PostgreSQL

**postgres_connections_active (gauge)**
Зачем: предотвратить исчерпание connection pool
Ярлыки: database, state

**postgres_query_duration_seconds (histogram)**
Зачем: найти медленные запросы
Ярлыки: database, query_type
Перцентили: p95, p99

**postgres_replication_lag_seconds (gauge)**
Зачем: контролировать актуальность данных на репликах
Ярлыки: database, replica

### 3.3 RabbitMQ

**rabbitmq_queue_messages (gauge)**
Зачем: обнаружить накопление необработанных сообщений
Ярлыки: queue, state

**rabbitmq_queue_messages_published_total (counter)**
Зачем: контролировать интенсивность потока
Ярлыки: queue

**rabbitmq_queue_messages_dlq_total (counter)**
Зачем: критичная метрика - показывает потерю заказов
Ярлыки: source_queue, reason

### 3.4 Инфраструктура

**node_cpu_usage_percent (gauge)**
Зачем: определить когда нужно масштабирование
Ярлыки: instance

**node_memory_usage_percent (gauge)**
Зачем: предотвратить OOM killer
Ярлыки: instance

**node_disk_usage_percent (gauge)**
Зачем: предотвратить переполнение диска
Ярлыки: instance, mountpoint

### 3.5 Бизнес-метрики

**orders_total (counter)**
Зачем: бизнес-дашборд, тренды роста
Ярлыки: source (web/api), status

**price_calculation_duration_seconds (histogram)**
Зачем: главное узкое место системы
Ярлыки: complexity
Перцентили: p95, p99, max

**price_calculation_queue_size (gauge)**
Зачем: контроль справляемости воркеров
Без ярлыков

**orders_lost_total (counter)**
Зачем: критичная метрика - должна быть 0
Ярлыки: reason, source

## 4. Настройка алертов

Критичные:
- orders_lost_total > 0
- rabbitmq_queue_messages_dlq_total растет
- http_requests_errors_total (5xx) > 10%
- API недоступен

Предупреждающие:
- price_calculation_queue_size > 100
- http_request_duration_seconds p95 > 2s
- node_cpu_usage_percent > 80% более 10 минут

## 5. Показатели насыщенности (Saturation)

Saturation покажет нам перегрузку ресурса и наличие очереди ожидания.

**RabbitMQ - очередь расчётов**
Порог: >50 сообщений (warning), >100 (critical)
Почему: 100 заказов = 8+ часов ожидания
Действия: добавить воркеры вручную или через auto-scaling, алерт команде

**PostgreSQL - пул соединений**
Порог: >70% от max (warning), >90% (critical)
Почему: исчерпание пула = 5xx ошибки для клиентов
Действия: проверить leaks, увеличить лимит, внедрить PgBouncer

**CPU load average**
Порог: >0.7 на ядро (warning), >1.0 (critical)
Почему: очередь процессов увеличивает latency
Действия: добавить инстанс через auto-scaling

**Disk I/O**
Порог: >50% времени занят (warning), >80% (critical)
Почему: замедляет БД и логирование
Действия: оптимизация запросов, upgrade дисков, read replicas

**Memory swap**
Порог: >100MB (warning), >500MB (critical)
Почему: swap в 100-1000 раз медленнее RAM
Действия: проверить leaks, увеличить RAM, рестарт приложения
