# Задание 3. Архитектурное решение по трейсингу

## 1. Мотивация

Текущие проблемы:
- Заказы в непонятном состоянии или зависают
- Сообщения теряются между системами
- Невозможно отследить путь заказа
- Диагностика проблем занимает часы

Технические метрики улучшения:
- MTTD: с часов до 1-2 минут
- MTTR: с часов до 10-15 минут
- Потерянные заказы: до 0%

Бизнес-метрики:
- Сохранение B2B контрактов
- Снижение жалоб на 60-80%
- Точный статус заказа для клиента

## 2. Проблемные места

Где заказ может сломаться:
1. Internet Shop → Shop API (сеть, таймауты)
2. Shop API → RabbitMQ (очередь недоступна)
3. RabbitMQ → CRM API (consumer не работает, DLQ)
4. CRM API → RabbitMQ (ошибка отправки)
5. RabbitMQ → MES API (очередь переполнена)
6. MES API → S3 (файл недоступен)
7. MES API → Расчёт цены (воркер упал, долгий расчёт)
8. MES API → БД (недоступна, deadlock)

## 3. Данные для трейсинга

Собираем для каждого заказа:
- order_id, trace_id, span_id, parent_span_id
- timestamp, duration
- service_name, operation_name, status, error_message
- source (web/api), customer_id, order_status
- file_3d_id, calculation_complexity
- http_status_code, queue_name, retry_count

## 4. Предлагаемое решение

Технологии:
- Jaeger - распределённый трейсинг
- OpenTelemetry - инструментация сервисов
- Elasticsearch - хранение трейсов

Компоненты:
1. Jaeger Collector - приём трейсов
2. Jaeger Storage - хранение в Elasticsearch
3. Jaeger UI - веб-интерфейс для просмотра
4. OpenTelemetry SDK в каждом сервисе

Интеграция:
- Shop API, CRM API - Spring Cloud Sleuth + OpenTelemetry
- MES API - OpenTelemetry .NET SDK
- RabbitMQ - плагин трейсинга

## 5. Компромиссы

Ограничения:
- Internet Shop (фронтенд) - браузерный трейсинг с ограничениями
- S3 - трейсим только операции API, не внутренности S3
- PostgreSQL - трейсим время запросов, без детализации SQL
- RabbitMQ - overhead 1-2% размера сообщения
- Производительность - overhead 2-5%, решение: sampling 10-20%
- Стоимость - Elasticsearch ~$100-200/месяц (оправдано предотвращением потерь)

## 6. Безопасность

Доступ:
- Аутентификация через LDAP/AD
- Роли: Developer, DevOps, Support, TechLead
- Только через VPN

Защита данных:
- Не логируем PII (ФИО, email, телефон)
- Логируем: order_id, customer_id (хеш), статусы
- Нет платёжных данных и паролей

Хранение:
- Elasticsearch в приватной подсети
- Шифрование at rest и in transit (TLS)


Audit: логи доступа к трейсам, алерт при подозрительной активности

## 7. Автоматический мониторинг и алертинг

Метрики из трейсов (отправляем в Prometheus):
- order_processing_duration_seconds - полное время обработки
- order_stage_duration_seconds - время на каждом этапе
- order_failures_total - количество ошибок
- order_stuck_total - застрявшие заказы (>1 час)

Алерты:
Critical: order_stuck_total > 5, order_failures > 10/min, duration p99 > 1 hour
Warning: duration p95 > 30 min, stage duration растёт

Схема на  [диаграмме](./jewerly_c4_model_with_tracing.drawio) (зелёным):
- Компонент "Span Metrics Processor"
- Связи: Jaeger → Processor → Prometheus → Alertmanager

Реализация:
- Jaeger Span Metrics Processor агрегирует метрики
- Grafana Dashboard "Order Journey" с визуализацией
- Auto-remediation: добавить воркер если очередь >1 час
