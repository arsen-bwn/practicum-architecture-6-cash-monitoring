# Архитектурное решение по кешированию

## 1. Мотивация

### Проблемы
1. **MES медленно загружает список заказов** - операторы жалуются на скорость работы первой страницы
2. **Долгий расчет стоимости** - 2-3 мин в среднем, до 30 мин для сложных моделей
3. **Растущая нагрузка** - +100 заказов каждый месяц, линейный рост

### Узкие места
- MES Dashboard: запрос с фильтрами + пагинация → JOIN, сортировка → 3-5 сек при 500+ заказов
- Расчет цены: CPU-intensive, повторные расчеты одинаковых моделей

### Что будем кешировать
1. **Список заказов для MES Dashboard** (по статусам + пагинация)
2. **Результаты расчета стоимости** (по hash 3D-модели)
3. **Статические справочники** (статусы, категории, шаблоны)

### Ожидаемый эффект
- Загрузка списка заказов: с 3-5 сек до 100-300 мс
- Повторный расчет цены для похожих моделей: 0 сек (из кеша)
- Снижение нагрузки на БД на 60-80%

## 2. Предлагаемое решение

### Технологии
**Redis** - in-memory key-value store, поддержка TTL, высокая производительность

### Решение 1: Комбинированное кеширование (РЕКОМЕНДУЕТСЯ)

#### Компоненты кеширования

**1. Серверное кеширование MES API (Cache-Aside)**
- Ключ: `orders:status:{status}:page:{page}`, TTL 10s
- Алгоритм: проверить Redis → если нет → запрос БД → сохранить → вернуть
- Почему Cache-Aside: простота, кеш не зависит от БД, свежие данные (10s lag)
- Write-Through не подходит: много записей, сложность
- Refresh-Ahead не подходит: сложно предсказать нужные страницы

**2. Кеширование расчета цены (Cache-Aside)**
- Ключ: `price:hash:{file_hash}:params:{params}`, TTL 7d
- Алгоритм: hash модели → проверить Redis → если нет → расчет (2-30 мин) → сохранить → вернуть
- Экономия до 80% расчетов

**3. Клиентское кеширование**
- HTTP Cache-Control для статики, Service Worker для MES SPA

### Стратегия инвалидации

| Стратегия | Описание | Применение |
|-----------|----------|------------|
| **TTL (временная)** | Кеш истекает через N секунд | Список заказов (10s), цены (7d) |
| **По событию (ключу)** | Удаление при изменении данных | Изменение статуса → DEL pattern |
| **Программная** | Явный вызов API инвалидации | Ручное удаление через админку |

#### Для списка заказов: TTL + по событию

**TTL 10 секунд:**
- Плюсы: простота, консистентность, операторы видят свежие данные
- Минусы: возможна задержка до 10 сек

**Инвалидация по событию:**
- Изменение статуса → удаляем кеши старого и нового статуса
- Создание заказа → удаляем кеш для статуса SUBMITTED
- Назначение оператора → удаляем кеш для статуса

**Почему не только TTL:**
- Операторы могут увидеть "залипший" заказ на 10 сек
- Комбинация TTL + event-based дает баланс

**Почему не только event-based:**
- Сложно отследить все изменения (обновления из CRM, внешние API)
- TTL страхует от забытых invalidations

#### Для расчета цены: TTL 7 дней

**Только TTL:**
- Цены стабильны, модели не меняются
- Длительный TTL = высокий hit rate
- Invalidation не нужна (расчет детерминированный)

## 3. Альтернатива: решение 2 (агрессивное кеширование)

**Отличия:** TTL 60s (вместо 10s), Refresh-Ahead (background job прогревает популярные страницы каждые 30s)

| Аспект | Решение 1 | Решение 2 |
|--------|-----------|-----------|
| TTL | 10s | 60s |
| Свежесть | Высокая | Средняя |
| Hit rate | 70-80% | 85-95% |
| Сложность | Низкая | Средняя |
| Stale data риск | Низкий | Средний |

**Решение 1 (рекомендуется):**
-  Простота, свежие данные (10s lag), легко масштабировать
-  Ниже hit rate

**Решение 2:**
- Высокий hit rate, мгновенные ответы
- Stale data до 60s, нужен background job, больше нагрузка

**Выбор:** Решение 1 - операторам важна свежесть (вознаграждение за новые заказы), 10s приемлемо, 60s нет

## 4. Детали реализации

**Структура ключей:**
- `orders:status:{status}:page:{page}` (TTL 10s)
- `price:hash:{file_hash}:params:{params}` (TTL 7d)
- `dict:statuses`, `dict:categories` (TTL 1h)

**Инвалидация:** при изменении статуса удаляем `orders:status:{old}:page:*` и `orders:status:{new}:page:*`

**Мониторинг:**
- Метрики: cache_hit_rate, cache_miss, latency_p95, memory
- Алерты: hit rate < 50%, latency > 10ms, memory > 80%

**Ресурсы:** ~25 MB активных данных, Redis 512 MB
